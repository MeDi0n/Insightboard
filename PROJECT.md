# О проекте

Этот файл описывает, что мы строим и зачем. Правила о том, как ты помогаешь мне работать, — в `CLAUDE.md`.

## Идея в одном предложении

Пользователь загружает файл с данными (для начала — CSV), а приложение с помощью AI автоматически превращает его в дашборд: набор графиков и таблиц.

## Как это работает (поток данных)

1. **Пользователь** заходит на страницу без всякой регистрации. Загружает CSV и задаёт настройки: сколько графиков нужно, при желании — текстовое пожелание («покажи продажи по месяцам»).
2. **Бэкенд** принимает файл, читает его и формирует запрос к AI-модели.
3. **AI-модель** смотрит на данные и решает, какие графики уместны. Возвращает **не картинку, а JSON — описание графиков** (тип, заголовок, какие колонки по осям).
4. **Валидация спеки.** Бэкенд проверяет ответ модели по строгой схеме: правильный ли тип графика, существуют ли указанные колонки в файле. Если ответ кривой — повторный запрос к модели с описанием ошибки.
5. **Фронтенд** получает валидную спеку и рендерит дашборд — раскладывает описание в набор графиков через библиотеку чартов.

AI здесь — аналитик, а не художник: он решает *что* показать. Рисует всё равно код фронтенда.

## Зачем этот проект

Учебный пет-проект для резюме (ищу первую работу как фронтенд-разработчик). Он собирает навыки, которые нужны на реальной работе: приём и обработка файлов, работа с долгими асинхронными операциями, интеграция с AI, валидация ненадёжных ответов, рендер данных, управление состоянием.

Таких решений на рынке много, поэтому проект ценен не идеей, а **видимой инженерией вокруг неё** — в первую очередь валидацией ответа AI по схеме и аккуратной работой фронтенда с состояниями.

## Стек

- **Фронтенд:** React. Серверный кэш — TanStack Query. Локальное состояние — обычный React Context. Плюс библиотека для графиков (выбрать на этапе планирования).
- **Бэкенд:** C# / ASP.NET.
- **Абстракция над провайдером AI:** код должен быть написан так, чтобы было неважно, к какой конкретно модели обращаться. Провайдер — заменяемая деталь, а не жёстко вшитая зависимость.

## Границы (важно соблюдать)

- **Формат файла на старте — только CSV.** PDF и Excel НЕ трогаем в MVP: извлечение таблиц из PDF — это отдельный большой проект, он утопит сроки. Excel можно добавить позже, если останется время.
- **Никакой авторизации в MVP.** Это добавляется позже (через Clerk), а не сейчас.
- **Перегенерацию отдельного графика по промпту НЕ делаем** пока — идея спорная, отложена.

## План по этапам

**Этап 1 — вертикальный срез (цель: ~неделя).**
Минимальный сквозной путь, который уже работает от начала до конца:
загрузка CSV + настройки → бэкенд → AI → валидная спека → рендер дашборда на фронте.
Без авторизации, без лишних фич. Результат сохраняется по ID и отдаётся на фронт. Это костяк, на который всё дальше наращивается.

**Этап 2 — устойчивость и состояния.**
Честная обработка асинхронной задачи на фронте: загрузка / готово / ошибка / повтор. Поведение на плохих данных: пустой CSV, кривая кодировка, большой файл, странные колонки. Пустые состояния, скелетоны.

**Этап 3 — фичи.**
Экспорт, редактирование данных, рефреш, авторизация через Clerk. Из списка выбираем 2–3, а не всё подряд.

**Этап 4 — упаковка.**
README со скриншотом и объяснением технических решений, деплой с рабочей ссылкой, пара тестов на ключевую логику (в первую очередь на валидацию спеки).

## Фуллстек, без перекоса

Это фуллстек-проект, и фронтенд с бэкендом одинаково важны — перевеса в сторону одного нет. Я хочу освоить обе стороны по-настоящему. Бэкенд: надёжный, типизированный, с осмысленной валидацией и обработкой ошибок. Фронтенд: аккуратные состояния, рендер, мобильная вёрстка, работа с сервер-кэшем. Качество вкладываю с обеих сторон, ни там ни там не срезаю углы.

## С чего начинаем

Не с кода. Сначала — архитектура: одна sequence-диаграмма потока «файл → бэкенд → AI → валидация → рендер» и набросок компонентов. Быстро, за час, не за два дня. Потом код.
